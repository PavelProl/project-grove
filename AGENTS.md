# project-grove

Сайт базы отдыха «Роща» у озера Парное. Цель — помочь гостю выбрать дом и обратиться к владельцам.
Проектные инструкции дополняют общие инструкции разработчика; отдельной политики моделей и skills здесь нет.

## Начало и продолжение

- Прочитай `.local/STATE.md`, если он есть; сверь задачу с веткой, HEAD и рабочими изменениями. При отсутствии записи восстанови контекст из чата, уточняя только недостающее. Публичный план не даёт разрешений.
- Команды, демо и фактическое состояние — в [README](README.md).
- Перед продуктовой или интерфейсной задачей прочитай относящиеся требования [брифа](docs/project-brief.md).
- Для выбора следующего шага читай [план](docs/PLAN.md) и проверь условия возврата отложенных вопросов; для причин прошлых изменений — [историю](docs/HISTORY.md) и связанные PR. Если задача в Issue, прочитай её и связанные результаты. Кратко сообщи состояние и следующий шаг.

## Границы и сдача

- Продуктовые, архитектурные и значимые процессные решения принимает разработчик. До реализации согласуй результат, границы и критерии; принятое повторно не согласовывай. В пределах задачи самостоятельно реализуй, проверяй и исправляй замечания. Анализ и ревью — без правки анализируемых файлов.
- Сохраняй чужую работу и игнорируемые материалы. Исключения перечислены в `.gitignore`; исходники, локальные заметки и настройки агента не публикуй. В сайт включай только выбранные подготовленные копии материалов. Секреты — вне Git; контакты и материалы — с согласия владельцев.
- Проверки выбирай по риску: для документации достаточно содержания, ссылок и diff; при изменении поведения запускай подходящие существующие сценарии, полный браузерный набор — при широком риске или выпуске. При ограниченных ресурсах сокращай параллельность и вывод. Для визуальных правок заранее определи показ результата; сохраняй требования поведения из брифа. Ручная визуальная приёмка разработчиком дополняет проверки агента; эмуляция не заменяет реальный телефон. Отдельное ревью — по риску или запросу.
- Пакет приёмки: файлы, diff, проверки, ограничения, итог ревью (если было), предлагаемый commit message и действия завершения. Продукт и визуал принимает разработчик.
- Commit, push, изменения Issues/PR, merge и внешние действия требуют явного разрешения в границах задачи; приёмка результата его не даёт. После согласованного commit сразу push; при неудаче сначала устрани причину. Самостоятельный результат или согласованная серия — отдельный PR; после merge синхронизируй локальную main.
- Основная папка остаётся на main, рабочая ветка — в worktree. Перед commit выполни fetch, сверь новые изменения правил и требований, состав индекса и весь публикуемый diff. `.local` должен игнорироваться и не отслеживаться.
- Документы и PR — на русском; коммиты — Conventional Commits на английском без подписей агента. Для описания PR используй доступный skill `pr` в рамках разрешений.

## Обновление документов

- Требования — в брифе, оставшиеся работы — в плане, фактическое состояние — в README. Каждый смысл хранится в одном основном месте. Новые документы и существенную перестройку сначала согласуй.
- Перед реализацией сверь выбранную работу плана с относящимися требованиями брифа, зависимостями и критериями. Рабочую задачу и исходную версию зафиксируй локально; не начинай зависимую работу без необходимых решений.
- При новой детали сначала предложи изменение и его влияние на объём. После согласования обнови требование в брифе и связанную работу либо отложенное решение в плане. Идея, исключение из версии и обязательство реализации — разные статусы; для отложенного указывай причину и условие возврата.
- При сдаче результата обнови затронутые документы к согласованной контрольной точке: README только при изменении фактических возможностей или использования, бриф при изменении требований, план при изменении оставшейся работы. Не объявляй реализованным то, что только согласовано.
- При завершении этапа сверь все разделы брифа с таблицей покрытия в плане: требование выполнено и проверено, имеет оставшуюся работу или явно согласованную отсрочку. Блокирующее выпуск требование нельзя закрыть отсрочкой без согласования изменения границ. Пересмотри условия возврата отложенных вопросов и предложи нужные решения. Совпадение ссылок не заменяет проверку смысла; завершённые работы уходят из оставшегося плана в Git/историю.
- Существенные принятые вехи записывай в историю: что, почему, ссылка на commit/PR. Для существенной ошибки добавь причину, вывод и исправление. Мелкие изменения достаточно отражать в Git. ADR создавай только для выбора с реальными альтернативами и дорогой сменой решения; в истории оставь ссылку.
- После согласования, существенного решения, проверки и перед ожиданием обновляй `.local/STATE.md`: задача, ветка/SHA, незавершённое, проверки, следующий шаг и разрешения. Это снимок, не дневник и не единственное место требований.
- При передаче агенту сообщи критерии, границы, разрешения и актуальные изменения. При изменении общего контекста обнови его версию и уведомь затронутых агентов.
